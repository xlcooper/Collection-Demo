# 业务代码运行与验证指南

> **维护规则（强制）**：本文只维护业务代码运行方式和各开发里程碑的服务器验证命令；当前状态、下一动作和完成判断仍以 `PROGRESS.md` 为准。命令或入口变化后应直接替换失效内容，避免追加相互冲突的临时说明。

## 当前运行入口约定

当前第一阶段端到端实验总入口是 `python scripts/run_object_memory.py`，负责串联批量图片、SAM3、Qwen、SQLite 和运行报告。`scripts/verify_m*.py` 只用于复现里程碑或定位单个环节，不是正式总入口。

所有面向用户的新增入口统一采用 `python scripts/<脚本名>.py [参数]`。项目代码由 Git 同步；依赖安装只在首次配置或依赖文件变化时单独执行和说明，不作为每次运行的固定步骤。后续不再新增依赖项目安装才能调用的控制台快捷命令。已完成的 M1/M2 历史命令不为此返工。

### 7.1 M3 输入输出接口与 workflow

历史 M3 报告使用过单次组合提示；当前 `verify_m3.py` 已随主流程更新为两阶段接口，用同一候选分别验证临时标注和参考图身份确认：

```text
M2 保留候选
  ├─ proposal_id、候选来源（M2 历史验收为类别提示；当前自动模式不提供类别）
  ├─ IMAGE_A_CANDIDATE：mask 隔离 crop，唯一临时标注目标
  └─ IMAGE_Z_CONTEXT_OVERLAY：只用于理解候选边界和场景位置
→ Qwen 候选分析调用（不输入任何对象卡片）
  ├─ ignored：阴影、反射、背景、纹理或不能独立成物体的局部
  └─ valid：输出临时 annotation，不判断 new / existing
→ valid 候选读取对象卡片文字
  ├─ 按粗/细类别、材质、颜色、形状、描述计算相关分
  └─ 只保留配置数量的 shortlist；当前默认8张
→ 记忆为空：直接 new
→ 记忆非空：Qwen 身份确认调用
  ├─ 输入临时 annotation、候选 crop、shortlist 卡片文字和 REFERENCE_IMAGE
  ├─ existing：返回 shortlist 中的准确 object_id
  ├─ new：没有卡片匹配
  └─ uncertain：证据不足或冲突；第二阶段不允许 ignored
→ 两阶段 JSON 分别做 schema、理由码和对象 ID 范围校验
→ M3 只写验证报告，不写 SQLite
→ M4 接入记录动作
  ├─ new：用本次 annotation 创建对象、首次观测和决策记录
  ├─ existing：向 matched_object_id 追加观测和决策记录
  ├─ ignored：记录候选终态和无效原因
  └─ uncertain：记录决策并进入 pending，不污染对象库
```

验证脚本运行两个场景：空记忆候选只调用一次分析并直接得到 `new`；同一视图卡片场景先调用一次分析，再调用一次身份确认。因此当前脚本真实总计3次 Qwen 推理。

本轮依赖没有变化，拉取代码后不需要再次安装项目：

`HF_HOME` 和 `HF_HUB_CACHE` 只是告诉脚本使用 M0 已下载并验证过的项目模型缓存；它们不会触发安装或下载。新终端需要重新设置这两个环境变量。

若服务器上的 `runs/m2` 已被清理，先按第 4 节重新运行 `python scripts/verify_m2.py` 生成资产，再执行 M3。M3 原始响应写入 `runs/m3` 并由 Git 忽略；机器可读报告写入：

## 10. M4 记忆闭环验证

M4 不再次调用 SAM3 或 Qwen，而是用确定性数据验证 M1–M3 之间的持久化接口。验证只使用临时记忆库，不会改动正式的 `data/memory`。

### 10.1 M4 写入接口与 workflow

```text
开始一次 run
→ 对源图 SHA-256 查询 SQLite
    ├─ 已 completed 或本批次已登记：返回 duplicate，整张图跳过
    └─ 未处理：登记 source 为 processing
→ 保存 M2 候选
    ├─ filtered：直接记录过滤原因，不调用 Qwen
    └─ 保留候选：交给当前 Qwen 两阶段接口
→ 接收已经通过 schema 校验并合并完成的最终决策
    ├─ new：创建一个 object，复制本次 crop/mask/overlay 为首次 observation
    ├─ existing：校验 matched_object_id 存在，只追加 observation
    ├─ ignored：记录 decision，proposal 进入 decided，不写 object/observation
    └─ uncertain：记录本次 attempt，proposal 保持 pending
→ pending 可使用同一个 proposal_id 和递增 attempt 再次提交判断
    ├─ 后续明确：按 new/existing/ignored 完成
    └─ 达到上层重试上限或处理异常：记录 failed
→ 每个候选的 proposal、decision、object、observation 在同一 SQLite 事务中写入
→ 图像资产先复制到 objects/<object_id>/observations/<observation_id>/；数据库失败时清理本次复制
→ 完成 source，汇总本 run 的图片、候选、四类决策、观测和活动对象计数
```

对象卡片查询返回全部 active 对象的结构化文字，并为每个对象附带配置数量的最近 crop 相对路径；当前 M5 先在脚本内对文字排序，只将 shortlist 的卡片和参考图输入 Qwen。M4 提供 pending/attempt/failed 的持久化机制；实际调用和异常重试由 M5 总流程调度。

## 13. M5 第一阶段真实批量验收

M5 使用当前总入口 `python scripts/run_object_memory.py` 把前四个里程碑串起来。它处理整个图片目录，不需要用户逐张确认，也不接收 `cup`、`mug` 等外部类别提示：

```text
递归读取输入目录中的 jpg/jpeg/png/webp
→ 逐图计算 SHA-256 并查询 SQLite
    ├─ 已处理或本批次重复：跳过
    └─ 新图片：保存源图索引
→ 加载一次 SAM3，依次处理所有新图片
    ├─ 项目脚本在整张图上自动铺设点网格
    ├─ SAM3 根据每个点产生 mask，用户不提供类别词
    ├─ 低置信、过小/过大、重复、被完整候选包含的局部或超量候选作为 filtered 写入 SQLite
    └─ 保留候选生成 mask 隔离 crop、mask、overlay
→ 释放 SAM3 和显存
→ 加载一次 Qwen
→ 每个保留候选先执行一次独立候选分析
    ├─ 输入 mask 隔离 crop 和 overlay，不输入对象卡片
    ├─ ignored：记录无效原因，不查询记忆、不做身份调用
    └─ valid：生成临时 annotation
→ valid 候选查询当时最新的全部对象卡片文字
    ├─ 脚本计算文字相关分，只保留默认前8张 shortlist
    ├─ 记忆为空：直接 new，不增加 Qwen 调用
    └─ 记忆非空：再调用一次 Qwen，输入候选 crop、临时 annotation、shortlist 文字和参考图
        ├─ existing / new：立即事务写入
        └─ uncertain：记录 pending；身份阶段禁止 ignored
→ 只有模型异常或 JSON 无法解析时才有限重试，默认最多 2 次
→ 释放 Qwen 和显存
→ 关闭 run，保存数据库摘要、逐图结果、模型耗时/显存和原始响应
```

因为对象卡片在每个 valid 候选完成临时标注后重新查询，所以前面候选刚建立的对象档案可以立即参与后续归并。SQLite 的全部卡片文字只在脚本内排序；Qwen 第二阶段只接收 shortlist 文字和对应的少量代表 crop，不遍历整个数据库。

这里的“无提示”是指用户和外部系统不提供物体类别。SAM3 官方仍是可提示分割模型，项目脚本会自动生成均匀采样点作为内部几何提示。它不是已经证明能穷举任意场景所有物体的官方模式，因此完整 M5 前先做 M5-A 候选校准，查看真实 crop/overlay 是否覆盖独立物体以及候选数量是否可接受。

### 13.1 准备验收图片

在服务器建立 `data/m5_input`，建议准备 10～20 张、每张以一个主要目标为主：

- 具体物体 A 的 3～4 个角度；
- 与 A 同类别但确实不同的物体 B 的 3～4 个角度；
- 可选的另一类别物体 C 的 2～3 个角度；
- 至少一份完全相同文件的副本，用于验证 SHA-256 跳过；
- 至少一张无效、遮挡严重、背景占主导或多物体复杂场景图片。

“完全相同副本”必须直接复制文件；重新截图或重新压缩后哈希会变化。现在无需按类别准备 `--prompt`，图片可以包含不同类别；但 M5-A 校准时应人工确认主要独立物体是否都产生了合理候选。

### 13.2 M5-A：先校准无类别提示候选

辅助验证脚本 `verify_m2.py` 不传 `--prompt` 时只运行 SAM3，不加载 Qwen，也不写正式 SQLite；它用于校准候选，不取代总入口。当前默认过滤 mask 面积超过整图 50% 的大区域，并过滤被更高分完整候选覆盖至少 90% 的较小局部 mask；无法可靠由几何规则区分的阴影留给 Qwen 候选分析阶段判断，ignored 后不会查询记忆或触发身份确认。

### 13.3 M5-B：先验证 Qwen 接管

gate v2 证明 mask 隔离 crop 已修复阴影误建档，但也证明单次混合提示会让对象卡片干扰候选有效性。当前接口已改为：先在不含记忆的输入中判断有效性并生成临时标注，再用文字 shortlist 和参考图确认身份。使用全新记忆库进行两阶段 gate；单图仍不加 `--validate-phase-one`：

```bash
cd /root/autodl-tmp/Collection-Demo
git pull origin main
conda activate "$PWD/.conda/envs/object-memory-demo"

python -m unittest discover -s tests -v

mkdir -p data/m5_qwen_gate_input
cp data/m5_input/m5a.jpg data/m5_qwen_gate_input/m5a.jpg

export HF_HOME="$PWD/weights/qwen"
export HF_HUB_CACHE="$HF_HOME/hub"

python scripts/run_object_memory.py \
  --input-dir data/m5_qwen_gate_input \
  --memory-root data/m5_two_stage_gate_memory_01 \
  --report environment/m5_two_stage_gate_report.json
```

`m5_two_stage_gate_memory_01` 是自动创建的独立实验记忆目录，不是模型版本。换新目录是为了避免旧 SQLite 中的图片哈希跳过同一场景。

本次通过条件：

- `grid_point_000131`、`000067`、`000155` 的 `candidate_analysis.validity` 为 `valid`，最终均为合理 `new`；
- `000208`、`000006`、`000100`、`000046` 在候选分析阶段直接 `ignored`，`memory_lookup_performed=false`、`identity_confirmation=null`；
- 预计共7次 analysis 调用；只有后两个有效物体在已有对象卡片时增加 identity 调用，因此预计2次 identity 调用；
- 报告中的 shortlist ID、相关分、临时标注和最终决策均可审查；没有 pending 或 failed。

若需要重跑，继续使用新的独立记忆目录。

### 13.5 M5 通过条件

- 全部单元测试通过；
- M5-A 报告确认不含外部类别提示，且代表场景中的主要独立物体具有可用 crop/mask/overlay；
- 报告 `status` 为 `passed`，普通 `checks` 与 `phase_one_coverage` 全部为 `true`；
- SAM3 已关闭后 Qwen 才加载，两个模型没有同时驻留；
- ignored 候选只经过 candidate analysis，不查询对象卡片、不执行 identity confirmation；
- valid 候选的文字 shortlist 不超过配置上限，identity 返回的 object ID 必须来自 shortlist；
- 至少形成 2 个新对象档案，说明同类不同实例没有全部错误合并；
- 至少出现 1 次 `existing`，说明同一物体的不同观测得到归并；
- 至少跳过 1 张完全重复图片；
- 至少记录 1 个 filtered 或 ignored 候选；
- 最终没有 pending 或 failed proposal；
- SQLite 中的 object、observation、decision 与逐图报告能够相互对应。

这些计数只能证明验收集覆盖了对应路径。是否确实为“同一具体物体”仍需结合用户准备的数据分组和报告中的逐图对象 ID 复核。
