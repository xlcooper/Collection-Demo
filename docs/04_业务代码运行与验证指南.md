# 业务代码运行与验证指南

> **维护规则（强制）**：本文只维护业务代码运行方式和各开发里程碑的服务器验证命令；当前状态、下一动作和完成判断仍以 `PROGRESS.md` 为准。命令或入口变化后应直接替换失效内容，避免追加相互冲突的临时说明。

## 后续运行入口约定

从后续新增功能开始，所有提供给用户的业务运行入口统一采用 `python scripts/<脚本名>.py [参数]`。项目代码由 Git 同步；依赖安装只在首次配置或依赖文件变化时单独执行和说明，不作为每次运行的固定步骤。后续不再新增依赖项目安装才能调用的控制台快捷命令。现有 M1/M2 命令保持不变，不为此返工。

## 1. M1 数据骨架验证

在 AutoDL 服务器仓库中执行：

```bash
cd /root/autodl-tmp/Collection-Demo
git pull origin main
conda activate "$PWD/.conda/envs/object-memory-demo"

python -m pip install --no-build-isolation --no-deps -e .
python -m unittest discover -s tests -v
python scripts/verify_m1.py
```

`verify_m1.py` 使用临时目录验证默认配置、六类核心数据、SQLite 重复初始化、六张空表和 CLI 状态查询，不会修改正式记忆库。验证结果写入：

```text
environment/m1_skeleton_report.json
```

随后初始化并重复打开正式的空记忆库：

```bash
object-memory init --json
object-memory init --json
object-memory status --json
```

默认生成以下本地运行资产，它们均被 Git 忽略：

```text
data/memory/
├── memory.sqlite
├── sources/
├── proposals/
├── objects/
├── raw_responses/
└── run_reports/
```

## 2. M1 通过条件

- 标准库单元测试全部通过；
- `environment/m1_skeleton_report.json` 的 `status` 为 `passed`；
- 连续两次 `object-memory init` 均成功；
- `object-memory status --json` 显示当前 schema version，六张核心表计数均为 0。

## 3. 回传规则

只提交服务器生成的 M1 报告，不提交 `data/memory`：

```bash
git status --short
git add environment/m1_skeleton_report.json
git commit -m "test: record M1 skeleton verification"
git push origin main
```

用户通知 push 完成后，本地 AI 必须先 pull，再依据报告判断 M1 是否完成并维护 PROGRESS、README 和 CHANGELOG。

## 4. M2 SAM3 流水线验证

M2 当前采用“显式类别提示列表”策略：对同一张图只编码一次，逐个运行配置的具体英文类别提示，再统一过滤和去重。它只覆盖配置类别，不宣称能够穷举开放场景中的所有物体。

在 AutoDL 服务器执行：

```bash
cd /root/autodl-tmp/Collection-Demo
git pull origin main
conda activate "$PWD/.conda/envs/object-memory-demo"

python -m pip install --no-build-isolation --no-deps -e .
python -m unittest discover -s tests -v
object-memory init --json

python scripts/verify_m2.py \
  --image data/smoke/scene.jpg \
  --prompt cup \
  --prompt mug
```

`object-memory init` 会把空记忆库从 schema v1 安全迁移至 v2。真实模型输出和生成的 crop、mask、overlay 位于 `runs/m2`，由 Git 忽略；机器可读报告写入：

```text
environment/m2_sam3_pipeline_report.json
```

## 5. M2 本轮通过条件

- 标准库单元测试全部通过，包含确定性的过滤、跨提示 mask 去重、资产生成和 schema 迁移测试；
- M2 报告 `status` 为 `passed`，所有 `checks` 为 `true`；
- 至少有一个原始候选和一个保留候选；
- 每个过滤候选都有原因，每个保留候选都有源图关联及 crop、mask、overlay；
- 报告明确保留 `configured categories only` 范围说明，不把当前策略称作开放场景穷举。

## 6. M2 回传规则

只提交 M2 报告，不提交 `runs/m2` 或 `data/memory`：

```bash
git status --short
git add environment/m2_sam3_pipeline_report.json
git commit -m "test: record M2 SAM3 pipeline verification"
git push origin main
```

用户通知 push 完成后，本地 AI 必须先 pull，再根据真实候选、过滤结果和资产证据判断 M2 是否完成。

## 7. M3 MLLM 流水线验证

M3 复用 `runs/m2` 中保留候选的 crop 和 overlay，不重新运行 SAM3，也不修改 SQLite。它先在空对象卡片列表下验证新对象标注，再把同一 crop 作为一张已知对象卡片的代表视图，验证 Qwen 能匹配回指定对象 ID。

本轮依赖没有变化，拉取代码后不需要再次安装项目：

```bash
cd /root/autodl-tmp/Collection-Demo
git pull origin main
conda activate "$PWD/.conda/envs/object-memory-demo"

python -m unittest discover -s tests -v

export HF_HOME="$PWD/weights/qwen"
export HF_HUB_CACHE="$HF_HOME/hub"
python scripts/verify_m3.py
```

`HF_HOME` 和 `HF_HUB_CACHE` 只是告诉脚本使用 M0 已下载并验证过的项目模型缓存；它们不会触发安装或下载。新终端需要重新设置这两个环境变量。

若服务器上的 `runs/m2` 已被清理，先按第 4 节重新运行 `python scripts/verify_m2.py` 生成资产，再执行 M3。M3 原始响应写入 `runs/m3` 并由 Git 忽略；机器可读报告写入：

```text
environment/m3_mllm_pipeline_report.json
```

## 8. M3 本轮通过条件

- 标准库单元测试全部通过，包含 JSON/schema 校验、对象 ID 范围保护、对象卡片分批和低置信匹配降级；
- M3 报告 `status` 为 `passed`，所有 `checks` 为 `true`；
- 空记忆判断为 `new`，并输出完整的物理对象标签而不是杯中内容；
- 同一视图对象卡片判断为 `existing`，且 `matched_object_id` 等于实际提供的卡片 ID；
- M3 不写入或修改 SQLite，实际对象新建与观测归并留到 M4。

只提交 M3 报告，不提交 `runs/m3`、`runs/m2` 或 `data/memory`：

```bash

git add environment/m3_mllm_pipeline_report.json
git commit -m "test: record M3 MLLM pipeline verification"

```

用户通知 push 完成后，本地 AI 必须先 pull，再根据真实标签、决策、耗时和显存证据判断 M3 是否完成。
