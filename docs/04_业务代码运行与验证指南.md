# 业务代码运行与验证指南

> **维护规则（强制）**：本文只维护业务代码运行方式和各开发里程碑的服务器验证命令；当前状态、下一动作和完成判断仍以 `PROGRESS.md` 为准。命令或入口变化后应直接替换失效内容，避免追加相互冲突的临时说明。

## 后续运行入口约定

从后续新增功能开始，所有提供给用户的业务运行入口统一采用 `python scripts/<脚本名>.py [参数]`。项目代码由 Git 同步；依赖安装只在首次配置或依赖文件变化时单独执行和说明，不作为每次运行的固定步骤。后续不再新增依赖项目安装才能调用的控制台快捷命令。现有 M1/M2 命令保持不变，不为此返工。

## 1. M1 数据骨架验证

在 AutoDL 服务器仓库中执行：

```bash
cd /root/autodl-tmp/Collection-Demo
git pull origin main
conda activate "$PWD/.conda/envs/object-memory-demo"

python -m pip install --no-build-isolation --no-deps -e .
python -m unittest discover -s tests -v
python scripts/verify_m1.py
```

`verify_m1.py` 使用临时目录验证默认配置、六类核心数据、SQLite 重复初始化、六张空表和 CLI 状态查询，不会修改正式记忆库。验证结果写入：

```text
environment/m1_skeleton_report.json
```

随后初始化并重复打开正式的空记忆库：

```bash
object-memory init --json
object-memory init --json
object-memory status --json
```

默认生成以下本地运行资产，它们均被 Git 忽略：

```text
data/memory/
├── memory.sqlite
├── sources/
├── proposals/
├── objects/
├── raw_responses/
└── run_reports/
```

## 7. M3 MLLM 流水线验证

M3 复用 `runs/m2` 中保留候选的 crop 和 overlay，不重新运行 SAM3，也不修改 SQLite。它先在空对象卡片列表下验证新对象标注，再把同一 crop 作为一张已知对象卡片的代表视图，验证 Qwen 能匹配回指定对象 ID。

### 7.1 M3 输入输出接口与 workflow

M3 保持单次组合推理：每个候选在每个对象卡片批次中只调用一次 Qwen，身份判断和标注共同写入一个 JSON，不增加第二次标注调用。

```text
M2 保留候选
  ├─ proposal_id、SAM 类别提示
  ├─ IMAGE_A_CANDIDATE：crop，身份比较主体和唯一标注目标
  └─ IMAGE_Z_CONTEXT_OVERLAY：原场景位置说明，禁止用于身份比较
+ 当前对象卡片批次
  ├─ object_id、已有结构化标签和描述
  └─ REFERENCE_IMAGE：该对象的少量代表视图
→ 构造一次 Qwen 输入，明确按以下顺序处理
  1. 候选有效性：无效物体 → ignored
  2. 实例身份：只比较 IMAGE_A 与 REFERENCE_IMAGE
  3. 当前标注：只描述 IMAGE_A
→ 一次返回受约束 JSON
  ├─ decision：new / existing / ignored / uncertain
  ├─ matched_object_id：仅 existing 必填
  ├─ confidence、reason_code、short_reason
  └─ annotation：new / existing 必填
→ schema、理由码和对象 ID 范围校验
→ 多批次保守汇总：存在唯一可靠匹配且无冲突才得到 existing；全部批次均无匹配才接受 new；冲突或低置信进入 uncertain
→ M3 只写验证报告，不写 SQLite
→ M4 接入记录动作
  ├─ new：用本次 annotation 创建对象、首次观测和决策记录
  ├─ existing：向 matched_object_id 追加观测和决策记录
  ├─ ignored：记录候选终态和无效原因
  └─ uncertain：记录决策并进入 pending，不污染对象库
```

验证脚本会运行两个独立场景：空卡片场景调用一次 Qwen；同一视图对象卡片场景再调用一次 Qwen。这里的两次调用用于测试两种输入场景，并不是对一个候选分别执行“身份调用 + 标注调用”。

本轮依赖没有变化，拉取代码后不需要再次安装项目：

```bash
cd /root/autodl-tmp/Collection-Demo
git pull origin main
conda activate "$PWD/.conda/envs/object-memory-demo"

python -m unittest discover -s tests -v

export HF_HOME="$PWD/weights/qwen"
export HF_HUB_CACHE="$HF_HOME/hub"
python scripts/verify_m3.py
```

`HF_HOME` 和 `HF_HUB_CACHE` 只是告诉脚本使用 M0 已下载并验证过的项目模型缓存；它们不会触发安装或下载。新终端需要重新设置这两个环境变量。

若服务器上的 `runs/m2` 已被清理，先按第 4 节重新运行 `python scripts/verify_m2.py` 生成资产，再执行 M3。M3 原始响应写入 `runs/m3` 并由 Git 忽略；机器可读报告写入：

```text

```

## 10. M4 记忆闭环验证

M4 不再次调用 SAM3 或 Qwen，而是用确定性数据验证 M1–M3 之间的持久化接口。验证只使用临时记忆库，不会改动正式的 `data/memory`。

### 10.1 M4 写入接口与 workflow

```text
开始一次 run
→ 对源图 SHA-256 查询 SQLite
    ├─ 已 completed 或本批次已登记：返回 duplicate，整张图跳过
    └─ 未处理：登记 source 为 processing
→ 保存 M2 候选
    ├─ filtered：直接记录过滤原因，不调用 Qwen
    └─ 保留候选：从 SQLite 读取 active 对象卡片及最近代表视图
→ 接收已经通过 M3 schema 校验的 Qwen JSON
    ├─ new：创建一个 object，复制本次 crop/mask/overlay 为首次 observation
    ├─ existing：校验 matched_object_id 存在，只追加 observation
    ├─ ignored：记录 decision，proposal 进入 decided，不写 object/observation
    └─ uncertain：记录本次 attempt，proposal 保持 pending
→ pending 可使用同一个 proposal_id 和递增 attempt 再次提交判断
    ├─ 后续明确：按 new/existing/ignored 完成
    └─ 达到上层重试上限或处理异常：记录 failed
→ 每个候选的 proposal、decision、object、observation 在同一 SQLite 事务中写入
→ 图像资产先复制到 objects/<object_id>/observations/<observation_id>/；数据库失败时清理本次复制
→ 完成 source，汇总本 run 的图片、候选、四类决策、观测和活动对象计数
```

对象卡片查询只返回结构化标签和配置数量的最近 crop 相对路径，不把完整数据库或所有历史图片塞给 Qwen。M4 提供 pending/attempt/failed 的持久化机制；实际何时再次调用 Qwen、最多重试几次由 M5 的总流程统一调度。


## 11. M4 本轮通过条件

- 标准库单元测试全部通过；
- M4 报告 `status` 为 `passed`，全部 `checks` 为 `true`；
- `new` 创建 1 个对象和首次观测，`existing` 复用同一对象并增加观测；
- 已完成源图的相同 SHA-256 被跳过，不增加 source、proposal、object 或 observation；

## 13. M5 第一阶段真实批量验收

M5 使用一个显式脚本把前四个里程碑串起来。它处理整个图片目录，不需要用户逐张确认：

```text
递归读取输入目录中的 jpg/jpeg/png/webp
→ 逐图计算 SHA-256 并查询 SQLite
    ├─ 已处理或本批次重复：跳过
    └─ 新图片：保存源图索引
→ 加载一次 SAM3，依次处理所有新图片
    ├─ filtered 候选直接写入 SQLite
    └─ 保留候选生成 crop/mask/overlay
→ 释放 SAM3 和显存
→ 加载一次 Qwen
→ 对每个保留候选读取当时最新的对象卡片
→ 每个候选、每个对象卡片批次执行一次组合判断与标注
    ├─ new / existing / ignored：立即事务写入
    └─ uncertain：记录 pending，不立即重复相同推理
→ 只有模型异常或 JSON 无法解析时才有限重试，默认最多 2 次
→ 释放 Qwen 和显存
→ 关闭 run，保存数据库摘要、逐图结果、模型耗时/显存和原始响应
```

因为对象卡片会在每个候选前重新查询，所以前面图片刚建立的对象档案，可以立即参与后面图片的身份比较。SQLite 仍只提供结构化标签和少量代表 crop，不会把整个数据库直接输入 Qwen。

### 13.1 准备验收图片

在服务器建立 `data/m5_input`，建议准备 10～20 张、每张以一个主要目标为主：

- 具体物体 A 的 3～4 个角度；
- 与 A 同类别但确实不同的物体 B 的 3～4 个角度；
- 可选的另一类别物体 C 的 2～3 个角度；
- 至少一份完全相同文件的副本，用于验证 SHA-256 跳过；
- 至少一张无效、遮挡严重或没有配置目标的图片。

“完全相同副本”必须直接复制文件；重新截图或重新压缩后哈希会变化。验收命令中的 `--prompt` 应覆盖图片里的目标类别，并使用具体英文名，例如 `cup`、`mug`、`bottle`。

### 13.2 服务器执行

本轮依赖没有变化，不需要安装：

```bash
cd /root/autodl-tmp/Collection-Demo
git pull origin main
conda activate "$PWD/.conda/envs/object-memory-demo"

python -m unittest discover -s tests -v

export HF_HOME="$PWD/weights/qwen"
export HF_HUB_CACHE="$HF_HOME/hub"

python scripts/run_object_memory.py \
  --input-dir data/m5_input \
  --memory-root data/m5_validation_memory_01 \
  --prompt cup \
  --prompt mug \
  --validate-phase-one \
  --report environment/m5_end_to_end_report.json
```

若数据中还有其他类别，继续增加相应的 `--prompt`。`data/m5_validation_memory_01` 是独立验收库，避免把测试图片写进正式 `data/memory`。如果修复后需要重跑，换用新的编号目录，例如 `data/m5_validation_memory_02`，避免旧哈希让所有图片被直接跳过。

### 13.3 M5 通过条件

- 全部单元测试通过；
- 报告 `status` 为 `passed`，普通 `checks` 与 `phase_one_coverage` 全部为 `true`；
- SAM3 已关闭后 Qwen 才加载，两个模型没有同时驻留；
- 至少形成 2 个新对象档案，说明同类不同实例没有全部错误合并；
- 至少出现 1 次 `existing`，说明同一物体的不同观测得到归并；
- 至少跳过 1 张完全重复图片；
- 至少记录 1 个 filtered 或 ignored 候选；
- 最终没有 pending 或 failed proposal；
- SQLite 中的 object、observation、decision 与逐图报告能够相互对应。

这些计数只能证明验收集覆盖了对应路径。是否确实为“同一具体物体”仍需结合用户准备的数据分组和报告中的逐图对象 ID 复核。
